04.1 · 기술적 도전

인덱스 설계 —
실험과 이론의 접점.

대상
공연 검색 목록 조회 API. 카테고리·지역·가격·공연 기간을 조건으로 받아 페이지네이션 결과 반환. 4개 테이블 JOIN(events · event_sessions · ticket_types · venues).
데이터
  • 5만 건의 이벤트, JDBC batch insert로 적재
  • 이벤트가 서울·경기에 집중 → 지역 카디널리티 비균등
  • 이벤트마다 진행 기간이 상이, 세션·티켓이 이벤트 기간 안에 분포
  • 등급별 좌석 가격 상이
핵심 부담
가장 사용 빈도가 높은 검색 API인데, 옵티마이저가 venues를 드라이빙 테이블로 잡으며 풀스캔에 가까운 동작.
접근
이론만으로 결정하지 않고 후보 인덱스 조합을 실제로 만들어 결과 비교. (1) 인덱스 조합 선정 → (2) 순서 변경 → (3) EXPLAIN 비교 실험 → (4) 최적 조합 추가 실험.
[ 인덱스 후보 11개 비교 표 + EXPLAIN 결과 표 자리 ]
결과
최종 선정: events(category, event_status, open_date) + ticket_types(event_session_id, ticket_type_status, price). 총 실행 시간 52.5ms → 0.906ms (약 58배), 드라이빙 스캔 27,500건 → 50건 (약 550배).
설계 결정
이론적 원칙(Equality 좌측 · 고카디널리티 우선 · Range 후방)을 지키면서도, 실제 EXPLAIN이 다르게 나오면 이론을 뒤집는다는 태도.

04.2 · 기술적 도전

시나리오 확장에서
발견한 트레이드오프.

처음 3개 시나리오(서울·경기 / 부산·경남·제주 / 전국)에서는 평균 91% 단축이라는 결과를 얻었습니다. 그런데 시나리오를 12개로 확장하자 다른 양상이 드러났습니다.

[ 시나리오 1 (조건 3개) vs 시나리오 2 (조건 12개) bar chart 자리 ]
발견
평균은 개선(-40%)됐지만 p95는 +5% 악화. 옵티마이저가 조건 조합에 따라 실행 계획을 다르게 선택하면서, 일부 조건에서는 새 인덱스가 기존 풀스캔보다 오히려 효율이 떨어졌습니다.
배운 것
시나리오 1 결과(91% 개선)만 보고 끝냈다면 운영 환경에서 일부 쿼리가 느려지는 걸 뒤늦게 알았을 것. 이후로는 단일 시나리오로 결론 내지 않고 다른 조건 조합을 함께 측정하는 걸 기본 절차로 삼았습니다.
설계 결정
"측정을 신뢰하려면 측정 자체를 먼저 의심해야 한다"는 걸 체득한 지점.

04.3 · 기술적 도전

캐싱 전략 비교 —
v1 / v2 / v3.

같은 jOOQ 쿼리를 호출하는 엔드포인트를 세 버전으로 만들어 캐시 레이어만 다르게 두고 비교.

v1캐시 없음 (DB 직접 조회)
v2Caffeine 로컬 캐시 (maximumSize=100, expireAfterWrite=5m)
v3Redis 분산 캐시 (GenericJackson2JsonRedisSerializer)
[ v1/v2/v3 응답 시간 분포 표 자리 ]
핵심 관찰
Local(Caffeine)이 Redis보다 약 1ms 빠름. 단일 응답만 본다면 Local이 우세. 그러나 max 항목에서 Redis가 더 안정적이었고, 멀티 인스턴스 환경에서는 Local 캐시가 인스턴스마다 다른 상태를 가질 수 있다는 점이 결정적.
설계 결정
1ms의 지연은 분산 환경의 일관성과 바꿀 만한 차이가 아님. 운영 관점에서 Redis 채택.
