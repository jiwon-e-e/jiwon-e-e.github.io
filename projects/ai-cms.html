02 · 기술적 도전

유동인구 감지 —
목업에서 실측으로.

문제
유동인구 값이 목업 센서 기반 가짜 데이터였음. 현장 카메라 영상에서 실제 인원수를 뽑아 대시보드/오토파일럿에 근거를 제공해야 함.
방식 결정
두 가지를 검토.
  1. 순간 카운트 — 그 프레임에 잡힌 사람 수를 그때그때 집계
  2. 재식별 트래킹 — 개별 인물을 인식·추적해 중복 카운트 제거
②는 동시 식별 인원이 최대 3명 수준으로 제한되고 비용도 급증해 현실성이 없다고 판단, ①을 채택.
하드웨어
촬영 장비로 라즈베리파이 + 웹캠 · 노트북 내장 카메라 · 아이폰 MJPEG 스트리밍(Simple IP Camera) · 안드로이드 USB 웹캠 모드를 각각 시도.
원안은 라즈베리파이에서 촬영·연산을 모두 처리하는 구조였으나, 보유 파이 사양이 낮아 AI 검출 코드가 돌지 않는 것을 확인.
→ 파이는 카메라 입력만, 연산은 별도 노트북이 담당하는 구조로 변경.
알고리즘
HOG → YOLO 교체.
초기 구현. OpenCV HOGDescriptor + 기본 SVM으로 5초 구간 최대 인원수를 집계해 백엔드로 POST.
문제. 실사용 테스트에서 여러 명을 보여줘도 카운트가 늘지 않거나, 가방을 사람으로 오검출하는 문제가 뚜렷.
교체. 예전 학부 프로젝트에서 자전거 인식에 YOLO를 썼던 경험을 근거로 ultralytics yolo11n으로 교체. COCO 클래스 중 class 0 (person)만 필터링하고 신뢰도 임계값을 설정해 오검출 축소.
→ HOG로는 뒷모습만 겨우 잡히던 수준에서 실사용 가능한 정확도로 개선.
백엔드 연동
검출된 인원수는 5초 주기로 POST. 백엔드에서는 값 소스별 우선순위를 명시.
수동 시뮬레이션 값 (1순위) → 카메라 실측 (2순위) → 목업 센서 (3순위)
캐시/DB에 저장하고 혼잡도 변화에 따라 알림·오토파일럿 로직을 트리거.
회고
초기 구현의 한계를 실측 테스트로 확인하고, 더 적합한 모델로 교체 판단을 내려 성능을 개선한 경험. "일단 만들고 실제 데이터로 검증한 뒤 바꾼다"는 흐름을 몸으로 익힘.

03 · 기술적 도전

실시간 카메라 스트리밍 —
WebSocket 전환과 3단계 트러블슈팅.

문제
대표님으로부터 "CCTV처럼 카메라 화면을 실시간으로 보고 싶다"는 신규 요구사항. 인원수 전송처럼 프레임을 매번 POST로 보내는 방식은 초당 10~15프레임 × 매 요청 헤더/핸드셰이크 부담이 커 구조 재설계 필요.
의사결정
1차. 로컬 서버를 외부에 노출하는 cloudflared 터널링으로 MJPEG 스트림을 띄워 요구사항은 충족.
한계. 세션이 끊길 때마다 공개 URL이 재발급되고 터미널 상주가 필요해 운영이 불편.
→ 이미 HTTPS로 세팅된 도메인을 활용해 WebSocket(wss) 기반으로 재구성하기로 결정.
1차

연결이 계속 강제 종료 (ConnectionAbortedError).

원인. Nginx에 /ws/ 프록시 규칙이 없어 요청이 백엔드로 넘어가지 못하고 Nginx가 자체 처리하다 끊음.

해결. 해당 경로를 백엔드로 넘기는 location 규칙 추가. 여기서 한 걸음 더 나가 IP 하드코딩 대신 이미 HTTPS로 세팅된 도메인의 프록시 엔드포인트(wss://)를 쓰도록 연결 방식 자체를 바꿔 보안성도 개선.

2차

핸드셰이크 자체가 실패 (WebSocketBadStatusException).

원인. Nginx가 클라이언트의 Upgrade 헤더를 백엔드로 전달하지 않음.

해결. proxy_set_header로 Upgrade/Connection 헤더를 넘기도록 설정 추가.

3차

연결은 정상인데 화면만 안 나오는 현상. 오류 로그도 없음.

원인. 로그·설정을 하나씩 뜯어 추적 → WebSocket 메시지 버퍼 기본값(8KB)이 JPEG 프레임 용량보다 작아 프레임이 조용히(에러 없이) 거부되고 있었음.

해결. 백엔드 WebSocket 설정에서 버퍼 크기를 1MB로 확장.

결과
사내 PC뿐 아니라 외부 네트워크의 휴대폰에서도 지연 없이 화면 확인. 요구사항 완전 충족.
설계 결정
기능을 붙이는 데 그치지 않고 초기 설계(cloudflared)의 운영상 한계를 스스로 인지해 더 확장 가능한 구조(WebSocket)로 전환을 주도. 명확한 에러 없이 실패하는 문제를 로그와 설정을 하나씩 뜯어 끝까지 추적해 해결한 경험.

04 · 부가 작업

ComfyUI 오케스트레이션 연동.

AI 영상 생성 스튜디오는 Sora-2를 주 경로로 하는 Spring Boot REST API 기반. 제안서 요건에 맞춰 ComfyUI를 CPU 전용 오케스트레이션 레이어로 얹고, 마지막 커스텀 노드가 기존 Sora API를 호출하는 구조로 연결했습니다. 화면은 ComfyUI 프론트를 CMS에 iframe으로 임베드.

05 · 회고

"기능이 된다"와
"운영이 된다"는 다르다.

cloudflared로 요구사항은 충족했지만 매번 URL이 바뀌고 터미널을 띄워둬야 하는 순간, 기능이 되는 것과 운영이 되는 것은 다른 문제라는 걸 체감했습니다. 한 달 동안 하드웨어부터 프론트까지 혼자 붙여보면서, 초기 설계의 한계를 스스로 인지하고 재설계하는 감각을 얻은 것이 가장 큰 수확입니다.
